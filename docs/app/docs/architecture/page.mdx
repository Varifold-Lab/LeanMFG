# Architecture

LeanMFG takes [MFGLib's finite MFG workflow](https://mfglib.readthedocs.io/en/stable/quickstart.html) as its functional baseline: define an environment and policy, induce a population, measure exploitability, and use an algorithm to find a policy. LeanMFG adds formal theory and proofs about those components. A completed case should make its assumptions explicit and connect as many parts of this chain as it actually proves:

> Model definitions → mathematical properties → algorithms → algorithm guarantees → application constraints.

## Correspondence with MFGLib

MFGLib's source separates [environments, policy helpers, scoring, and algorithms](https://github.com/radar-research-lab/MFGLib/tree/main/mfglib). We use those **capabilities** as the baseline, while Lean files are also separated by their proof role.

| MFGLib capability | LeanMFG today | Coverage |
| --- | --- | --- |
| Environment: initial law, reward, transition | `Computational/Environment.lean` | General finite horizon, multidimensional states/actions, population-dependent rewards and transitions |
| Policy and induced mean field | `Computational/Policy.lean` | Time-indexed joint state–action laws and forward recursion |
| Scoring by exploitability | `Computational/QFn.lean` | Optimal/policy Q values, greedy policy, exploitability |
| Equilibrium solvers | `Computational/Algorithms/` | Fictitious Play, OMD, Prior Descent, MFOMO, OMI |
| Built-in environments | `Computational/Environments.lean` | All ten upstream models, including its weighted rock-paper-scissors |
| Tuning and persistence | `Computational/Tuning.lean` | Native metrics, candidate/random search, frozen parameters, and JSON |

The [MFGLib port guide](/docs/computational) records its pinned source version, numerical checks, API mapping, backend differences, and remaining gaps. Its shared sums and dot products now have [FloatLib-backed error proofs](/docs/numerical). Whole-solver correctness and convergence are not yet proved. Existing rational models and the continuous HJB modules retain their proofs and interfaces.

## Code layers

The mathematical modules are grouped by role, then by setting: `Static/`, `FiniteState/`, or `Continuous/`. The general executable MFGLib workflow is grouped in `Computational/`, with its own model, policy, algorithm, and tuning modules. Future proofs can refer to these definitions without replacing the runtime implementation.

| Layer | Responsibility |
| --- | --- |
| [Model](/docs/model) | Environments, policies, distributions, costs, dynamics, and admissibility |
| [Theory](/docs/theory) | Equilibrium concepts, equations, and mathematical results |
| [Algorithm](/docs/algorithm) | Executable best responses, scoring, and equilibrium checks |
| [Computational](/docs/computational) | General finite-horizon environments, numerical solvers, scoring, and tuning |
| [Numerical](/docs/numerical) | Executable arithmetic, stored-value interpretation, and rounding conventions; proofs live in `Verification/Numerical/` |
| [Verification](/docs/verification) | Proofs about algorithms, optimality, and invariants |
| [Examples](/docs/examples/rock-paper-scissors) | Concrete models with proved or executable checks |

`LeanMFG.lean` imports the library and proved examples. `lake build` checks these imports; `lake exe mfglib_check` builds and runs the separate numerical reference checks, and `lake exe mfglib` provides the numerical command-line interface.

## Mathematical scope

General theory can include equilibrium, best responses, dynamic models, HJB equations, and population evolution. Existence, uniqueness, and optimality each require stated hypotheses. An executable solver additionally needs a proof connecting its result to the mathematical definition; convergence and error bounds are separate claims.

Applications can add finance, energy, transport, or other settings once their agents, states, actions, population dependence, and objective are specified. Transformer and DeFi are possible application directions, not existing MFG models in this library.

Application requirements have different logical roles. **Population mass conservation** is an invariant of the finite-state update under normalized transitions. **Market clearing** may instead be an equilibrium constraint. **Solvency** needs its own assumptions and proof. We state each property in the form that matches its model.

## Current results and boundaries

- The [static rock-paper-scissors case](/docs/examples/rock-paper-scissors) certifies an executable checker and proves that the uniform rational distribution is the unique exact equilibrium.
- The [finite-state case](/docs/examples/finite-state-left-right) proves mass conservation for any sequence of admissible policies and normalized transitions. Its Left/Right game has a verified exact equilibrium.
- The [deterministic HJB case](/docs/examples/hjb) proves a classical verification theorem and an optimal feedback path for one explicit control problem.

These proofs do not yet certify the general numerical solvers or a coupled HJB–population system. A bridge from continuous real-valued theory to grid or floating-point computation will need a formal approximation or numerical error result.

## Next integration: shared semantics and numerical refinement

The next development target is a finite-horizon congestion game with Fictitious
Play and a certified exploitability bound. The existing numerical port and its
reference tests provide the executable baseline. The table distinguishes the
implemented numerical primitives from the remaining integration targets.

| Component | Responsibility | First acceptance condition |
| --- | --- | --- |
| `Model/FiniteState/FiniteHorizon` | Exact real-valued laws, joint occupancies, policies, population-dependent rewards/transitions, deviations, and equilibrium | Time and terminal conventions match the computational model; prove the actual forward update preserves mass |
| Numerical interpretation | Interpret finite stored values, normalize a returned policy into an exact mathematical policy, record tolerances | State a precise relation between approximate arrays and exact distributions |
| FloatLib adapter | Binary64 reductions and one-step population coordinate/L1/mass-drift bounds are implemented | Next: verify policy-to-joint-population construction, multi-step error propagation, and Bellman expectations |
| Differentiation adapter | Optional derivative operations for algorithms that need them | Ordinary environment evaluation and Fictitious Play work without a Dual callback; MFOMO's derivative provider is explicit |
| `Verification/FiniteState` | Bellman optimality, forward/backward numerical error propagation, and certificate soundness | A successful checker implies an ε-equilibrium statement for the exact policy represented by the output |

The mathematical core should distinguish a state law from a state–action joint
law. For the MFGLib convention, reward/policy indices are `Fin (T+1)` and
transition indices are `Fin T`. An individual deviation holds the population
flow fixed. A candidate equilibrium uses the flow induced by its own policy.
Adapters for existing examples must explicitly check their payoff and terminal
conventions; the continuous HJB model remains a separate theory module.

### Reusing the Lean ecosystem

The dependency audit on 2026-09-26 inspected FloatLib commit
[`5f8218dc`](https://github.com/lean-dojo/FloatLib/tree/5f8218dc571c01d6f8bd070c65bcd0de3a40b3c5)
and TorchLean commit
[`de3192df`](https://github.com/lean-dojo/TorchLean/tree/de3192df4779877ceb65cfe470a4d4ce9d480a5b).
Both require Lean 4.34.0 and mathlib 4.34.0. LeanMFG now uses that toolchain,
pins mathlib to `5ed2965256430c3649e86755f9576b54eca72435`, and includes the
audited FloatLib revision in its dependency manifest. TorchLean is not yet a dependency.

FloatLib supplies scalar semantics and rounding theorems. LeanMFG's current
left-fold proofs compose its half-ULP addition and multiplication bounds for the
actual binary64 operations. Runtime finiteness checks discharge the hypotheses
when they accept. FloatLib also provides
`FloatLib.Numerics.ReductionTree` to record evaluation schedules, and
`abs_eval_sub_exact_le_errorBudget` composes local arithmetic errors at the nodes
actually used. This is directly relevant to population updates and Bellman
expectations; applying it still requires the local finiteness and error
hypotheses for the selected operations.

TorchLean provides candidate tensor and autograd interfaces. Its own
[trust-boundary document](https://github.com/lean-dojo/TorchLean/blob/de3192df4779877ceb65cfe470a4d4ce9d480a5b/docs/TRUST_BOUNDARIES.md)
distinguishes exact graph/tape theorems, floating-point approximation, and native
backends. A prototype must establish which path LeanMFG actually uses. TorchLean's
audited manifest pins FloatLib to `c9a051f08f948ce473036b815b0669fafb61f601`, so a
combined integration needs one tested shared revision. CSLib or Physlib should
be introduced with a specific reused definition or theorem and a concrete caller.

### The first complete proof path

1. Establish the general model and Bellman optimality over exact distributions.
2. Connect a finite congestion instance and its executable Fictitious Play update
   to that model through the numerical interpretation.
3. Bound forward population error, reward/transition evaluation error, backward
   value error, and any error from interpreting or normalizing the returned policy.
4. Certify an upper bound on exploitability against the population genuinely
   induced by that exact policy. Acceptance at ε then implies ε-equilibrium.

An exploitability bound against an approximate population alone does not finish
step 4: the proof must account for its difference from the exact induced flow.
The first instance can use affine congestion rewards and fixed transitions;
population-dependent transitions additionally need a suitable sensitivity bound.
Convergence of Fictitious Play remains a separate theorem with model-specific
hypotheses. Successful output certification can be useful before that theorem
is available.
